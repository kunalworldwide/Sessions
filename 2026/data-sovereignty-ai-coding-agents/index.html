The Problem

Three surfaces where your code leaks.

\uD83D\uDCC4
SURFACE 01
Source Code in Transit
Every file the agent reads \u2014 schemas, configs, secrets in comments, internal APIs \u2014 travels to the model provider's inference endpoint. Often across borders.
\uD83E\uDDE0
SURFACE 02
Context as Training Fuel
Your codebase, architecture patterns, and business logic become context. Whether it's retained, logged, or used for training depends entirely on the vendor's terms \u2014 which change.
\uD83D\uDD12
SURFACE 03
Generated Code Provenance
When an agent writes code, who owns the output? Is it derived from your proprietary patterns? Is it license-clean? Can you prove it in an audit?
REGULATORY REALITY

GDPR, DPDP Act 2023 (India), CCPA, and EU AI Act all impose data residency and processing obligations. "The vendor said it was fine" is not a compliance strategy.

Sovereignty Framework

Four pillars of code sovereignty.

A practical framework for evaluating any AI coding tool \u2014 not just Kimchi.

PILLAR 01
Data Residency
Code and prompts processed in a region you control. No cross-border inference. DPDP Act and GDPR compliant by architecture.

Zero Retention

Actionable

Your AI coding sovereignty checklist.

Ask these questions before letting any AI coding agent touch your codebase.

\u2705
Where does inference happen? Can the vendor prove your code stays in your region, or does it route to an unknown cloud?
\u2705
What is the retention policy? Are prompts and outputs stored? For how long? Can you enforce zero-retention at the architecture level?
\u2705
Can your data be used for training? Is it contractually prohibited AND architecturally impossible? "We don't train on your data" in a privacy policy is not enough.
\u2705
Can you self-host? If compliance requires full sovereignty, can you run the entire stack \u2014 agent, models, inference \u2014 inside your VPC?
\u2705
Is there a per-request audit trail? Can you see exactly what was sent, to which model, for what purpose, by whom?
