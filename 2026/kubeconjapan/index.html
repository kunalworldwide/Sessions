What if multi-cluster looked like one?

Liqo uses an extended Virtual Kubelet to make a peered remote cluster appear as a single virtual node in your home cluster.

Pods scheduled onto that virtual node actually run in the remote cluster.

The scheduler you already run doesn't change. The topology does.

#KubeCon #CloudNativeCon
The unlock is a mental-model flip. Normally a node is one machine. Liqo — an open-source multi-cluster project that started at Politecnico di Torino — extends the Virtual Kubelet so an entire remote cluster shows up in your home cluster as a single virtual node. When the scheduler places a pod there, Liqo runs it in the remote cluster. Your scheduler and manifests are untouched. We didn't add a scheduler; we changed the shape of the cluster.

Offloading, precisely

  1. 1 One Virtual Kubelet per peered cluster — each remote gets its own VK instance with its own negotiated identity kubeconfig; the provider caps you to the negotiated resource slice (CPU/mem/pods/GPU).
  2. 2 Twin namespace + twin pod — offloading extends the namespace across the boundary (twin namespace on the remote); a pod on the virtual node executes as a twin pod there.
  3. 3 Resource reflection — objects the pod needs are reflected into the twin namespace: Services, EndpointSlices, Ingresses, ConfigMaps, Secrets, PVCs/PVs — endpoint IPs remapped.
  4. 4 ShadowPod CR — a custom resource in the remote cluster enforces the pod's presence even during a control-plane partition.

Status, logs, exec all reflect back to the local pod — you troubleshoot it like it's local.

#KubeCon #CloudNativeCon
Let me earn trust with internals. Four mechanics, all in Liqo's docs. One: each remote cluster gets its own Virtual Kubelet with its own kubeconfig, and the provider enforces the resource slice you negotiated. Two: Liqo extends the namespace — a twin namespace on the remote, your pod runs there as a twin pod. Three: resource reflection copies Services, EndpointSlices, ConfigMaps, Secrets, even PVCs, and remaps endpoint IPs. Four: the ShadowPod CR lives in the remote cluster and enforces the pod's existence even if the control planes can't talk. Payoff: status, logs, and kubectl exec reflect back, so you debug it like it's next door.

No new scheduler. Just labels you already know.

apiVersion: v1
kind: Pod
metadata:
  name: finetune-run-42
spec:
  nodeSelector:
    gpu-type: h100          # land on H100 capacity
  affinity:
    nodeAffinity:           # prefer on-prem, tolerate cloud spot
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: capacity
                operator: In
                values: ["on-prem"]
  tolerations:
    - key: "spot"           # allow scheduling onto spot virtual nodes
      operator: "Exists"

This pod has no idea it might run in another cloud.

#KubeCon #CloudNativeCon
The CFP promised an honest networking comparison — no favorite. Cilium Cluster Mesh: direct pod-to-pod over eBPF, great IF you run Cilium everywhere and control CIDRs, because it hard-requires non-overlapping pod and service CIDRs. Liqo's fabric: WireGuard, CNI-agnostic, and it'll remap overlapping CIDRs — which saved us on clusters we didn't provision. Trade-off: Liqo routes through a gateway, so that's your throughput chokepoint. Calibration: intra-cluster is sub-millisecond, cross-cluster encrypted lands ~12–18 ms depending on region — measure your own. Rule: Cilium everywhere with clean CIDRs → Cluster Mesh. Mixed CNIs or messy CIDRs → Liqo fabric.

One queue that sees everything

Kueue + a Liqo virtual-node topology isn't documented together. Teams wire it up blind.

  • ResourceFlavor ← a named class of nodes selected by node labels; one per GPU class (a100 / h100 / spot), mirroring the Slide-9 virtual-node labels
  • ClusterQueue ← cluster-scoped quota pool, nominal quota per flavor (+ borrow/preempt policy)
  • LocalQueue ← namespaced pointer developers submit to (kueue.x-k8s.io/queue-name)

Kueue gates, it does not place. Job created suspend: true → quota check → suspend: false → the real Kubernetes scheduler places it (onto a virtual node, via Slide-10 affinity).

Because Liqo made 5 clusters look like 1, ordinary single-cluster Kueue spans all GPUs.

#KubeCon #CloudNativeCon
Requirement three: one global queue. First the mechanic, because it matters: Kueue does not schedule pods. A job arrives created suspended; Kueue checks its ClusterQueue quota; only then it un-suspends and hands off to the real scheduler — the same one from slide 10 that lands it on a virtual node. Gate, then place. The mapping: a ResourceFlavor is a named class of nodes by label, so one per GPU class — A100, H100, spot — mirroring the virtual-node labels. One ClusterQueue holds global quota across every virtual node. Developers submit to a namespaced LocalQueue and never think about where capacity lives. And it works because Liqo already collapsed five clusters into one — no exotic cross-cluster queuing needed.

"But wait — isn't there MultiKueue for this?"

Path A — MultiKueue

A manager cluster DISPATCHES jobs to separate worker clusters; each worker is its own scheduling domain; job is cloned, first admit wins, others deleted (AllAtOnce / Incremental dispatch).

Path B — Liqo + Kueue (ours)

ONE scheduling domain; Kueue admits once; the real scheduler places across virtual nodes; pods offload transparently.

MultiKueue: better when clusters must stay fully independent (different teams, no shared network).    Liqo + Kueue: better when you want one topology, transparent pod networking, vanilla affinity placement.

Same problem, two philosophies. We chose one scheduling plane.

#KubeCon #CloudNativeCon
Sharp folks are thinking: Kubernetes already has MultiKueue — why Liqo? MultiKueue dispatches jobs: a manager clones your job to independent worker clusters, first admit wins, the rest are deleted; clusters stay separate worlds. Liqo + Kueue is one scheduling plane, remotes are nodes, and the ordinary scheduler places with the affinity you saw. MultiKueue shines when clusters must stay independent. We wanted one topology with transparent networking and plain affinity, so we chose the virtual-node plane. Neither is wrong — know which problem you have.

Two failure modes, two behaviours — know both

Namespace offloading decides WHICH workloads may travel.
Node affinity + Liqo cluster labels decide WHERE (pin sensitive jobs to capacity=on-prem, let only burst spill to spot).

Case A — whole remote cluster unhealthy

  • Liqo health-checks each peering (foreign API server + VPN tunnel).
  • Virtual node → NotReady after node-monitor-grace-period (default 40s).
  • Remote pods' EndpointSlices marked not-ready → Services stop routing to the dead cluster.

traffic continuity (ShadowEndpointSlice)

Case B — single remote WORKER NODE fails (cluster up)

  • By default, offloaded pods sit in Terminating INDEFINITELY and are NOT auto-replaced.
  • Fix: controllerManager.config.enableNodeFailureController=true (since v0.7.0) → force-deletes the stuck pod → ShadowPod controller recreates it on a healthy node.

pod re-creation = opt-in

Traffic reroutes on cluster failure; pod re-creation on node failure is opt-in. Set the flag.

#KubeCon #CloudNativeCon
Honest mechanics, two cases. Setup first: namespace offloading decides which workloads may travel, node affinity on Liqo's labels decides where — we pin sensitive to on-prem, let only burst spill to spot. Case A: a whole cluster dies. Liqo health-checks the API server and VPN tunnel; the virtual node goes NotReady after the default 40s, then remote EndpointSlices go not-ready so Services stop sending there. That's real and automatic — but it's TRAFFIC continuity. Case B, write this down: if a single remote worker node fails while the cluster's up, by default the pods sit in Terminating forever and are NOT replaced. Fix is one Helm flag — enableNodeFailureController — so Liqo force-deletes the stuck pod and ShadowPod recreates it on a healthy node. Default off. Turn it on. That's the line between 'we have DR' and DR that works.
